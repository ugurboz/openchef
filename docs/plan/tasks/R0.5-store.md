## Goal

The durable state of OpenChef: one SQLite database in WAL mode, forward-only embedded
migrations, and repositories for tasks, steps, attempts, sessions and turns whose state
changes are compare-and-set, so a crash at any point can be resumed (§11, D-018).

## What to build

1. **Open:** `Store::open(path) -> Result<Store, Error>`; rejects bad paths; creates the
   file with mode 0600 on Unix; `journal_mode=WAL`, `foreign_keys=ON`,
   `busy_timeout`; `rusqlite` with feature `bundled`.
2. **Writer actor (D-030):** one `tokio` task owns the write connection and runs write
   commands one at a time (`enum WriteCmd` + `oneshot` reply). Reads go through a small
   pool of read-only connections (`query_only=ON`). Blocking SQLite calls run inside
   the actor's own thread or `spawn_blocking`, never on the async executor directly.
3. **Migrations:** embedded with `include_str!`, applied in a transaction each, recorded
   with a checksum; errors `InvalidMigration`, `SchemaTooNew`, `MigrationModified`
   exactly like the Go code; a failed migration leaves no trace.
4. **Repositories:** every Go method of `tasks.go` and `attempts.go`
   (`create_task`, `task`, `tasks(filter)`, `transition_task(id, from, to, change)`,
   `set_plan`, `set_workspace`, `steps`, `transition_step`, `start_attempt`,
   `end_attempt`, `running_attempts`, `record_session`, `open_session`,
   `set_session_process`, `close_session`, `live_sessions`, `begin_turn`, `end_turn`,
   `in_flight_turn`, …). Transitions are compare-and-set: `UPDATE … WHERE status =
   from`, and zero rows → `Error::Conflict { expected, actual }`. Transition legality is
   checked with `openchef-core`'s `check_transition` before writing.
5. **Errors:** `Error::{NotFound, Conflict{..}, Transition(..), InvalidMigration,
   SchemaTooNew, MigrationModified, Sqlite(..), Io(..)}` with `thiserror`.
