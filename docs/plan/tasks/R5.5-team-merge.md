## Goal

A pipeline task in `team` mode runs its independent steps side by side, each in its own
worker worktree, and a merge queue integrates finished steps into the task's integration
branch one at a time (rebase → verify → fast-forward). `openchef merge <task>` brings a
finished task's branch into the user's branch on request. `pipeline` gets `--mode` and
`--importance` (#52).

## Design (D-041)

### Scheduling

1. **Dependencies from scopes:** step *j* waits for every earlier step *i* whose `files`
   overlap its own (equal paths, or one a directory prefix of the other). A step with no
   `files` overlaps everything: it waits for all earlier steps and all later ones wait
   for it. So a plan without scopes runs exactly as `isolated`.
2. **Workers:** at most `Limits::team_workers` (default 3) steps run at once; a ready
   step starts when a slot is free, lowest index first. Each worker is the existing step
   loop (§7.2 retries, failover, review, breakers) on its own worktree, spawned as its
   own Tokio task.
3. **A failing step never stops the others** (§7.5): a worker that would park the task
   reports instead; steps that depend on it do not start; when nothing can run any more
   the task parks with the first worker's reason (`waiting_quota` with the earliest
   resume time if every stop was quota, else `needs_attention`).

### Worktrees and branches

4. Integration worktree `<worktrees>/<repo>/<task>` on `openchef/<task>`, as `isolated`.
   Worker worktree `<worktrees>/<repo>/<task>.steps/step-N` on `openchef/<task>-step-N`,
   created from the integration branch's tip when the step starts. (§8 said
   `<task>/step-N` and `openchef/<task>/step-N`; the first would nest a worktree inside
   the integration worktree, the second cannot coexist with the ref `openchef/<task>`.)
5. A worker commits its step on its own branch; the step stays `running` until the
   queue integrates it, then becomes `verified` with the integrated commit.

### Merge queue

6. One at a time, in the order steps finish: in the worker worktree `git rebase` onto
   the integration branch; clean → the step's verification runs there; passing →
   `git merge --ff-only` of the step branch in the integration worktree.
7. **Conflict or failing verification** → the rebase is aborted, the step's commit is
   saved as a patch, the worker worktree is reset to the integration tip and the step
   runs again with the conflict (files, or verification output) and the patch as its
   message. At most `Limits::max_retries` integration retries per step; then the step
   fails.
8. **Recovery:** the queue keeps no state of its own. A step is integrated when the
   integration branch has its commit (trailers); finished when its step branch has one;
   otherwise its worker resumes as today (carry-over).

### `openchef merge <task>`

9. For a `done` task: in the user's repository, refuse on a detached HEAD or a tree with
   tracked changes; fast-forward to `openchef/<task>` when possible, else
   `git merge --no-ff --no-edit`; a conflict is aborted and reported with its files. The
   only command that writes the user's working tree (§8.2). Daemon method `task.merge`.

### CLI

10. `openchef pipeline --mode isolated|team --importance low|normal|high|critical`;
    `status` shows the mode; the live renderer shows `step_integrated` events
    (`integrated`, `conflict`, `verify_failed`).

## Scope

- `crates/openchef-gitws` — worker worktrees, rebase with conflict files, ff-only merge,
  merge into the user's branch
- `crates/openchef-engine` — team scheduler and merge queue (`team.rs`), worker runs,
  event `step_integrated`, `Limits::team_workers`, `RunRequest::mode`
- `crates/openchef-api`, `crates/openchef-daemon` — `mode`, `importance` params,
  `task.merge`
- `crates/openchef-cli` — `--mode`, `--importance`, `merge`
- `docs/architecture.md` §8 — worker paths and branch names

## Acceptance criteria

- [ ] Two steps with disjoint scopes run at the same time in two worker worktrees and
      both are integrated; the task is done with both commits on `openchef/<task>`.
- [ ] Overlapping scopes run in order.
- [ ] A rebase conflict sends the step back with the conflict; the retry integrates.
- [ ] A failing step leaves independent steps running; the task needs attention after.
- [ ] A daemon restart during team work resumes without repeating integrated steps.
- [ ] `openchef merge` fast-forwards a clean tree, merges otherwise, refuses a dirty tree
      and reports a conflict.
- [ ] `pipeline --mode team --importance high` reaches the task (#52).
