## Goal

`openchef pipeline "<goal>"` asks a planner agent, in `plan` permission mode, for a
plan of up to seven steps; OpenChef validates it strictly, gives one repair turn on
invalid output, and stops in `awaiting_approval`. The user reads the plan with
`openchef plan <task>`, approves, rejects or edits it, and an approved plan runs step by
step exactly like `run` does today. Council, review and audit come with R5.2–R5.4.

## Design (D-037)

1. **Agent work that is not implementing a step.** Planners (and later critics,
   reviewers, arbiters, auditors) start processes that must be recorded before the
   first write (§5.1) and recovered after a daemon crash, like attempts. Attempts gain a
   `role` (`implement`, `plan`, `review`, `council`, `arbiter`, `audit`); task-level
   roles use step index 0. Migration 0003 rebuilds `attempts` without the foreign key
   to `steps` (a plan does not exist before it is made) and keeps one running attempt
   per (task, step, role).
2. **States.** `planning` becomes an active state (an engine run drives it, so attempts,
   sessions and approvals are allowed). New transitions: `planning →
   waiting_quota | needs_attention`, and `waiting_quota | needs_attention → planning`
   for a task without an approved plan. `retry` resumes into the state the task left.
3. **Plan phase.** The engine runs a planning attempt: a session in `plan` mode (the
   daemon's session spec forces `plan` while the task is planning, so the approver's
   evaluator refuses edits too), one turn with the plan schema as structured output.
   The answer is `TurnResult.structured`, else the final text parsed as JSON (a
   fenced block is accepted). Validation is strict: unknown fields refused, 1–7 steps,
   non-empty title and prompt, importance in the vocabulary, files relative and inside
   the repository. On failure one repair turn in the same session quotes the errors;
   a second failure parks the task in `needs_attention` with the raw answer in the
   event log. Quota and crash failures follow §7.2 failover like implement attempts.
4. **Approval.** A valid plan is stored with `set_plan` and the task moves to
   `awaiting_approval`. `openchef plan <task>` prints it (`--json` for the plan
   document); `plan approve <task>` moves it to `running` and starts the engine;
   `plan reject <task> [reason]` cancels it; `plan edit <task>` opens `$VISUAL`/`$EDITOR`
   on the plan as JSON and stores the edited version after the same validation.
   `pipeline --yes` approves a valid plan without stopping (unattended mode builds on it).
5. **Run.** An approved pipeline runs its steps with the existing step loop; with no
   review yet it ends `done` (R5.2 inserts review and the `reviewing` state).

## Scope

- `crates/openchef-core` — `AttemptRole`, task transitions, `is_active`, the plan document
  type and its validation
- `crates/openchef-store` — migration 0003, attempts with roles
- `crates/openchef-engine` — the plan phase, service `pipeline`, `plan`, `approve`,
  `reject`, `edit`
- `crates/openchef-api`, `crates/openchef-daemon` — `task/pipeline`, `plan/*` methods
- `crates/openchef-cli` — `pipeline`, `plan`
- `crates/openchef-fake` — a structured answer for a turn, if missing

## Acceptance criteria

- [ ] `openchef pipeline` with a fake planner produces `awaiting_approval` and the plan
      prints with each step's title, importance and verification.
- [ ] Invalid plan → one repair turn → valid plan; invalid twice → `needs_attention`
      with the raw answer in `openchef logs`.
- [ ] `plan approve` runs every step to `done`; `plan reject` cancels; `plan edit`
      refuses an invalid edit and stores a valid one.
- [ ] The planner's session is in `plan` mode and an edit request during planning is
      denied by the approver.
- [ ] Kill the daemon during planning: the restarted daemon kills the planner process and
      plans again in the same conversation (resume) or a new one.
- [ ] Store migration keeps existing attempts (role `implement`).
